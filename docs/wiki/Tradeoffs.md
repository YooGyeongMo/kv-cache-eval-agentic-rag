근거가 코드 주석, 이슈, PR, 실측 결과에 남아 있는 결정만 적었습니다.

| # | 상황 | 선택지 | 결정 | 비용 | 다시 볼 조건 |
|---|---|---|---|---|---|
| 1 | 보고서의 숫자와 인용을 검증해야 함 | LLM 채점기 / 코드 검증기 | **코드 검증기** (`verify`). 앞선 실험에서 LLM 채점기가 틀린 숫자 23건 중 2건, 21건 중 1건만 잡음 | 정규식 거짓 양성 (`Gen5를`, 대소문자, 기준선 오탐)을 계속 고쳐야 함 | 수치가 아닌 논리 비약을 봐야 할 때 LLM 채점을 보조로 추가 |
| 2 | 검색이 실패했을 때 재시도 방식 | 같은 질의 재검색 / 재작성 먼저 / k 확장 먼저 | **k 확장 → 재작성** 순서. 같은 질의 재검색은 같은 문서를 돌려줬고, k를 넓히자 정답 27에서 30 | 재시도마다 LLM 호출(grade)이 늘어남 | 문서 풀이 커져 k 확장의 잡음이 커지면 재작성을 먼저 |
| 3 | 논문에 없는 사실을 찾으려 할 때 | 웹 폴백 / 근거 없음으로 남김 | **문서 풀 질의에는 웹을 열지 않음**. 웹 폴백을 열자 문서 질문 오답이 1에서 7로 늘었음 | seed 0 보고서에 `근거 없음` 3곳 | 논문 밖 근거가 필수인 항목이 늘면 웹 질의 템플릿을 추가 |
| 4 | 한국어 질의로 영문 논문을 찾아야 함 | 다국어 모델에 맡김 / 한국어 특화 모델 / 질의 번역 | **검색 직전 영어로 번역** (`localize`). 번역 시 상위 3모델 Hit@5 0.95로 수렴 | 질의마다 LLM 호출 1회 추가, 번역 품질에 검색이 의존 | 문서 풀에 한국어 자료가 섞이면 원문 질의와 번역 질의를 함께 검색 |
| 5 | 오픈소스 임베딩 선정 | 리더보드 상위 / 한국어 특화(KURE-v1) / 실측 | **실측으로 bge-m3**. 영어 하이브리드 MRR 0.930으로 최고, KURE-v1은 한국어 질의에서도 0.80으로 bge-m3(0.85)보다 낮음 | 경량 모델 대비 색인 3.5배 느림 (24.6초 대 6.9초) | 색인을 자주 다시 해야 하는 환경이면 경량 모델 재검토 |
| 6 | 조밀 검색과 BM25를 섞는 방식 | 점수 가중합 / RRF | **RRF (k=60)**. 점수 정규화가 필요 없고 문서 수가 달라져도 덜 흔들림. 앞선 실험에서 `EnsembleRetriever` weights도 가중 RRF였음 | 점수 크기 정보는 버림 | 한쪽 검색기의 점수가 매우 신뢰할 만하면 가중합 실험 |
| 7 | 벡터 인덱스 | FAISS / numpy 전수 코사인 | **numpy 행렬 + rank-bm25 직접 구현**. 청크 211개라 전수 비교로 충분하고 `where` 필터와 RRF를 한 함수에서 다룸 | 대규모에서 느림, faiss-cpu 의존성이 목록에 남아 있음 | 청크가 수만 개로 늘면 FAISS로 교체 |
| 8 | 참고문헌 작성 | LLM 생성 / 근거 원장에서 기계 생성 | **기계 생성** (`attach_reference`). LLM이 없는 arXiv 번호와 무관한 문서를 올렸음 (#5) | 논문 서지는 `pool.json`에 사람이 적어야 함 | 없음. 서지 대조는 `tools/qa.py`가 arXiv 원본과 계속 확인 |
| 9 | 기술 선정 사유 서술 | LLM이 맥락에서 작성 / 사람이 쓴 문장 주입 | **주입** (`selection_note`). 재료가 없을 때 LLM이 임베딩 선정 이야기를 지어냄 (#13) | 선정 사유를 바꾸려면 `config.py` 수정 | 평가 대상을 에이전트가 고르게 바꿀 때 |
| 10 | 4갈래 병렬 평가가 같은 State를 갱신 | 한 키에 리스트 누적 / 관점별 키 + 기술 하위 키 | **관점별 키 분리 + `merge_by_key`** | State 스키마가 길어짐 | 관점이 늘어나면 키 대신 `dict[관점][기술]` 한 키로 묶는 것 검토 |
| 11 | 웹 검색 무료 한도 소진 | 매번 검색 / 결과 캐시 | **질의 키 캐시, TTL 14일, 빈 결과는 저장 안 함**. 역방향 실행이 28회 모두 캐시 적중 | 14일 안에는 새 시장 정보를 못 봄. 캐시는 재배포 문제로 저장소에 넣지 않음 | 시장 정보가 빠르게 바뀌는 주제면 TTL을 줄임 |
| 12 | 확증편향 확인 | LLM에게 중립 여부 질문 / 셀 수 있는 지표 | **감사 노드가 찬반 수, 근거량 비율(2배), 시장성 웹 근거 0건을 셈** | 서술의 뉘앙스 편향은 못 잡음 (금지어로 일부 보완) | 금지어로 못 잡는 기울어진 서술이 레드팀에서 나오면 규칙 추가 |
| 13 | 순서 효과 확인 | 1회 실행 / 순서 뒤집어 2회 | **2회 실행** (`order_seed` 0, 1) | LLM 비용과 시간이 2배 | 비교 대상이 3개 이상이 되면 순열 전부는 비싸므로 무작위 순서 몇 회로 |
| 14 | 되돌이 루프 상한 | 무제한 / 상한 | **감사 재수집 1회, 보고서 재작성 2회**. 넘기면 그 사실을 한계 장에 적고 진행 | 상한 안에서 못 고친 지적이 남을 수 있음 (seed 0 생성 직후 2건) | 정정기(`repair.py`)로 못 고치는 지적이 반복되면 상한을 늘림 |
| 15 | 검증기 지적을 고치는 방법 | 매번 LLM 재생성 / 규칙이 분명한 것만 기계 정정 | **기계 정정, 추측 교정 금지**. 크레딧이 막혔을 때 지적 6건을 0건으로 (#11) | 판단이 필요한 서술은 손대지 못함. 깨진 스크래핑으로 `15.5`를 `14.99`로 만든 적이 있어 추측 경로를 막음 (#14) | 정정 규칙이 늘어 검증기와 판정이 어긋나기 시작하면 판정 함수를 다시 하나로 모음 |

## 생성기와 채점기를 나눈 이유

`llm.py`는 생성(gpt-4.1-mini)과 종합, 보고서(gpt-4.1)를 나눕니다. 같은 모델이 쓰고 같은 모델이 판단하면 자기 글을 너그럽게 보기 때문입니다. 다만 숫자는 어느 모델에도 맡기지 않고 코드로 대조합니다.

## 기술 선정 기준

진입 비용의 대칭성으로 골랐습니다. MLA는 하드웨어를 두고 모델을 바꾸고, ITME는 모델을 두고 하드웨어를 바꿉니다. 같은 진영에서 둘을 고르지 않았고(TurboQuant, KIVI 제외), 진영 분류가 흐려지는 후보(InfiniGen)와 상용 채택 근거가 비어 시장성 관점이 한쪽으로 비는 후보(PIM/CXL)를 뺐습니다 (`config.NOT_SELECTED`).
